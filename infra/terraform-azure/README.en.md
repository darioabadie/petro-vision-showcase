# ClickHouse cluster on Azure — replication and sharding via Terraform

*[Versión en español](README.md)*

**Scope:** a self-contained infrastructure module exploring ClickHouse operations in high availability. Provisions, with Terraform, on real Azure infrastructure, a 2-shard × 2-replica ClickHouse cluster coordinated by ClickHouse Keeper, seeded with real data from the main pipeline (`analytics.fact_well_monthly_production`), so sharding, replication, and failover can be exercised beyond the single-node ClickHouse the pipeline runs day to day. **Does not modify or depend on** `docker-compose.yml`, `dbt/`, `pipeline/`, or the root `Makefile` — it lives entirely isolated under `infra/`.

⚠️ **This creates real, billable Azure resources** (VMs, public IPs, networking) until `terraform destroy` is run. See [Cost](#cost) below.

## Topology

```
                         ┌─────────────┐
                         │   Keeper    │  10.0.1.10
                         │ (coordinator)│
                         └──────┬──────┘
                    ┌───────────┴───────────┐
              ┌─────▼─────┐           ┌─────▼─────┐
   Shard 1    │ ch-s1-r1  │◄─────────►│ ch-s1-r2  │   (replicas of each other)
              │10.0.1.11  │  replica  │10.0.1.12  │
              └───────────┘           └───────────┘
              ┌───────────┐           ┌───────────┐
   Shard 2    │ ch-s2-r1  │◄─────────►│ ch-s2-r2  │
              │10.0.1.13  │  replica  │10.0.1.14  │
              └───────────┘           └───────────┘

   well_production_distributed (Distributed, sharded by cityHash64(well_id))
   points at well_production_local on all 4 nodes.
```

Each node gets its `macros` (`{shard}`, `{replica}`) generated by Terraform via `templatefile()` — there are no 4 hand-written configs, there's one parameterized definition (`local.ch_nodes` in `locals.tf`) that the 4 resources come from via `for_each`.

## Why this design

- **Keeper, not Java Zookeeper**: it's the current ClickHouse standard, lighter, and the coordination mechanism any new cluster would use today.
- **`ReplicatedReplacingMergeTree` + `Distributed`**: the same pattern a 100PB production cluster would use, at laptop/small-VM scale.
- **Same schema as the real pipeline**: `well_production_local` mirrors the columns, `ORDER BY`, and `ver_column` (`_record_version`) of `analytics.fact_well_monthly_production` (`dbt/models/core/fact_well_monthly_production.sql`) — not an invented toy dataset.

## Requirements

- Azure CLI logged in (`az account show`) with an active subscription.
- Terraform `1.16.1` (`brew tap hashicorp/tap && brew install hashicorp/tap/terraform`).
- `jq`, `docker`, `ssh` locally.
- An SSH key at `~/.ssh/id_ed25519_azure{,.pub}` (or override `admin_ssh_public_key_path` / `SSH_KEY`).
- The main pipeline up and populated (`make up && make dbt` at the repo root) — that's where the real seed data comes from.

## Commands

```bash
cd infra/terraform-azure

export ARM_SUBSCRIPTION_ID=$(az account show --query id -o tsv)

terraform init
terraform plan      # review before applying — these are real resources
terraform apply

# Schema (once, propagates to all 4 nodes via ON CLUSTER):
NODE1_IP=$(terraform output -json node_public_ips | jq -r '."ch-s1-r1"')
docker run --rm -i clickhouse/clickhouse-server:24.8 clickhouse-client \
  --host "$NODE1_IP" --port 9000 --multiquery < sql/01_create_replicated_tables.sql
docker run --rm -i clickhouse/clickhouse-server:24.8 clickhouse-client \
  --host "$NODE1_IP" --port 9000 --multiquery < sql/02_create_distributed_tables.sql

# Real data from the main pipeline:
./scripts/export-seed-data.sh
./scripts/load-seed-data.sh

# Real replication tests (not just "it's up"):
./scripts/test-replication.sh

# When done:
terraform destroy
```

`scripts/test-replication.sh` runs and verifies, in order:
1. Insert into `well_production_local` on `ch-s1-r1` → confirm it shows up on `ch-s1-r2` (real replication).
2. Stop node `ch-s1-r2` (`systemctl stop pvm-clickhouse` over SSH) → confirm `well_production_distributed` still returns the full count from the surviving replica.
3. Restart `ch-s1-r2` → confirm it resyncs on its own (`system.replicas.is_readonly = 0`, counts match again).
4. Compare `sum(oil_m3)` between the cluster (`well_production_distributed`) and the main pipeline's single-node ClickHouse (`analytics.fact_well_monthly_production`) — must match exactly. This proves sharding didn't drop or duplicate rows.

Exits non-zero if any of the 4 checks fails.

## How this scales

Change `shard_count` or `replicas_per_shard` in `variables.tf` (or pass `-var`) and run `terraform apply` again:

```bash
terraform apply -var="shard_count=3"
```

`locals.tf` regenerates the `ch_nodes` map from those two variables; `nodes.tf` has a single `resource ... for_each = local.ch_nodes` — Terraform creates the new VMs with their config auto-rendered, without touching any other file. It's the same mechanism you'd use to provision on AWS/GCP instead of Azure: only the provider changes.

## Cost

With the defaults (2×2 + 1 Keeper): 4× `Standard_B2s` + 1× `Standard_B1s` ≈ USD 0.18/hour of compute, plus 5 Standard SKU public IPs (this subscription doesn't allow Basic SKU anymore — Azure is retiring it; Standard costs a few extra cents/hour). Running `terraform destroy` between work sessions keeps total cost to a few dollars.

## What's missing for production-real

Named on purpose, not implemented (out of scope for a laptop/small-VM cluster):

- **TLS** between nodes and on client ports (everything here is plaintext HTTP/TCP).
- **Single-node Keeper** — no fault tolerance for Keeper itself; real production uses 3 (or 5) for Raft quorum.
- **Remote state** — `terraform.tfstate` is local here; production would use a remote backend (Azure Storage Account + blob lease instead of AWS's S3+DynamoDB) for locking and team collaboration.
- **Monitoring/alerting** (ClickHouse Prometheus exporter, `system.backups`).
- **NSG open to the operator's IP** for SSH/ClickHouse — fine for a single operator, not for a team.

## Security

NSG rules restrict SSH and ClickHouse ports to the public IP of whoever runs `terraform apply` (resolved at apply time via `data "http" "my_ip"`, not hardcoded), and inter-node traffic to the VNet range. Even so, these are public-IP VMs on a real cloud — don't leave them up longer than needed.
